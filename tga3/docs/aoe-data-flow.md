# AOE 题目数据与按变化调度

## 数据职责

| 数据 | 当前权威来源与用途 | Scout / Worker 如何使用 |
|---|---|---|
| PostgreSQL `task_runs` | 原题 ID、题面、难度、连接/提交说明；收集与解题状态、尝试、预算到期时间。系统用它调度和恢复，不要求智能体访问数据库 | Scout 通过登记工具提交；系统根据记录给 Worker 分配题目 |
| PostgreSQL `input_files` | 附件索引、大小、哈希及宿主路径；附件正文在该题 `inputs/` | 系统把该题附件只读挂载到 Worker 的 `/inputs` |
| PostgreSQL 单题黑板 | 题面、公共接口/凭证、附件说明、靶机运行提示，以及 Finding 等共享内容 | 通过原生 Hook 交付到 CLI 上下文；首次交付相关记录，之后按已确认位置增量交付 |
| 批次 `questions.json` | 系统写入的题目清单与 `collection_complete`。也包含各题 target 配置 | Scout 控制程序读取 `/aoe/questions.json`，判断收集是否完成、登记数量是否增长；Worker 不挂载此文件 |
| 单题 `question.json` | 题面、附件相对路径、尝试/报告状态的文件快照；其中 `target` 是靶场接口配置的文件持久化来源，不能概括为纯数据库副本 | 靶场模块在缓存缺失时从文件恢复 target；Worker 不直接挂载或读取此文件 |
| `target-instances.json` | 系统持久化靶机租约、当前地址、配额等待、清理/重试状态 | 系统提供当前目标地址给 Worker；启动、关闭及配额管理由系统执行 |

普通题目字段存在数据库与 JSON 的重叠；本次按已批准的 R04 方案保留现有职责，没有进行数据库到文件的存储迁移。`target` 配置不写入题目的 SQL metadata，继续保存在文件中。

## 登记到执行的流程

1. Scout 读取批次上传或平台接口，下载单题附件，调用 `scout_register_questions`。
2. 系统登记题目信息和附件索引，将题面/附件说明发布到该题黑板，写入单题 `question.json` 和批次 `questions.json`。登记回执只包含该次登记的题目，不返回整批清单。
3. Scout 的控制程序读取清单中的数量及完成标记。收集过程可以继续；新题登记会唤醒调度器，系统仍按已有优先级、收集阶段限制及靶机配额规则派发。
4. 需要动态靶机时，系统先准备实例；就绪后原子认领题目并记录尝试。将公共接口与凭证、当前靶机提示放入该题黑板；Worker 的原生 Hook 将黑板内容交付给 CLI。动态靶机地址也通过当前 CLI 输入提供。
5. Worker 从 CLI 上下文了解题目，直接读取 `/inputs` 附件。它不直接查询 PostgreSQL，也不依赖读取两个题目 JSON 文件来认领。第一次实际动作启动解题预算。
6. Worker 在自己的工作区保存结果，在 `/findings` 写 Finding。系统校验证据、导入黑板；新的最终候选会唤醒调度器，结束尝试、清理靶机并生成报告。

黑板交付使用 JSON 文本表示记录，但它不是读取磁盘 `question.json` 的结果。

## R04 的工作量控制

- 每轮调度只读取一份题目列表，在本轮复用认领、超时、解出后的返回记录；父任务阶段和 Worker/Reporter 状态真正变化时才 UPDATE。
- 单题快照先比较相关输入字段与靶机状态；无变化时跳过视图组装、JSON 编码、哈希和文件写入。附件索引缓存到附件登记发生变更；重复清单内容不重写。
- 存储层在成功提交题目、智能体、附件或黑板变更后发进程内通知。模型工具动作本身不必触发全量巡检；Token 统计、黑板 ACK 等无关元数据不会唤醒调度器。
- 调度使用 `asyncio.Event`，并按最近的尝试截止或靶机重试时间唤醒。靶机准备/关闭任务完成、Scout 结束/失败会唤醒；网络操作保持在原有后台任务中。
- 默认每 5 秒校准一次权威状态。附件采用一次批量查询校准，避免按题逐个查询；校准也会发现遗漏通知、缺失快照文件和服务恢复后的状态。事件等待不推迟预算截止。
- 并发认领锁和数据库原子 metadata 变更保留。批次退出时清理视图、附件与唤醒缓存；`question.json` 的靶场配置和两个文件的既有读取方保留。

本通知只负责当前控制进程的低延迟唤醒，不是跨进程消息队列；周期校准仍是可靠性兜底。没有引入 Redis、Celery、新服务或数据库结构迁移。
