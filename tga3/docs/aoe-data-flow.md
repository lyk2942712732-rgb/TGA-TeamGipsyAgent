# AOE 题目数据与按变化调度

## 数据职责

| 数据 | 当前权威来源与用途 | Scout / Worker 如何使用 |
|---|---|---|
| PostgreSQL `task_runs` | 原题 ID、题面、难度、连接/提交说明；收集与解题状态、尝试、预算到期时间。系统用它调度和恢复，不要求智能体访问数据库 | Scout 声明字段映射与已提供的契约，系统请求题单并登记；系统根据记录给 Worker 分配题目 |
| PostgreSQL `input_files` | 附件索引、大小、哈希及宿主路径；附件正文在该题 `inputs/` | 系统把该题附件只读挂载到 Worker 的 `/inputs` |
| PostgreSQL 单题黑板 | 题面、本题连接/提交说明、附件说明、靶机运行提示，以及 Finding 等共享内容 | 通过原生 Hook 交付到 CLI 上下文；首次交付相关记录，之后按已确认位置增量交付 |
| 批次 `questions.json` | 系统写入的题目清单与 `collection_complete`。也包含各题 target 配置 | Scout 控制程序读取 `/aoe/questions.json`，判断收集是否完成、登记数量是否增长；Worker 不挂载此文件 |
| 单题 `question.json` | 题面、附件相对路径、尝试/报告状态的文件快照；其中 `target` 是靶场接口配置的文件持久化来源，不能概括为纯数据库副本 | 靶场模块在缓存缺失时从文件恢复 target；Worker 不直接挂载或读取此文件 |
| `target-instances.json` | 系统持久化靶机租约、当前地址、配额等待、清理/重试状态 | 系统提供当前目标地址给 Worker；启动、关闭及配额管理由系统执行 |

普通题目字段存在数据库与 JSON 的重叠；本次按已批准的 R04 方案保留现有职责，没有进行数据库到文件的存储迁移。`target` 配置不写入题目的 SQL metadata，继续保存在文件中。

## 登记到执行的流程

1. Scout 分别读取批次总览原文 `/task-overview/scene.md` 和 `/task-overview/task.md`，必要时读取用户上传的 API 说明。只调用 `scout_collect_questions(plan)` 请求用户明确提供的题单接口，不再逐题重写题面。原生工具只允许读取这些提供的说明，不能用 shell、浏览器或脚本猜测附件、详情、文档、前端或靶机接口；内置网页搜索关闭。
2. `plan.request` 包含已提供的接口及实际凭证；`fields` 指定原始 ID、标题、题面、难度等字段路径；`target`、`submission` 是已给定接口的共享模板，`{unique_code}` 等按原题字段展开，`{flag}` 留给提交模块。未知附件入口留空；不下载、不探查。明确要求的 VPN 连通预检由程序先执行，通过后才取题单。
3. 系统原样保存每题题单条目至 `source.json`，登记题目信息、已有本地附件索引，发布本题题面/连接/提交信息，写 `question.json`（含 `source_path`）和批次 `questions.json`。明确分页仅允许题单返回的同源同路径下一页 URL；可用 `total_path` 校验覆盖数量。完整登记后自动标记收集完成，回执只返回数量和完成状态，Scout 立即停止。新题登记唤醒调度器，仍按已有优先级和配额规则派发。
4. 需要动态靶机时，系统先准备实例；就绪后原子认领题目并记录尝试。当前靶机提示、本题信息和协作增量通过 Hook 交付；动态地址也通过当前 CLI 输入提供。
5. **公共原文分开读取**：批次黑板保留完整场景说明和初始用户提示词；文件 `overview/scene.md`、`overview/task.md` 保留原文并只读挂载为 `/task-overview/`。Worker 新 CLI 上下文开局分别完整读取一次，含接口和凭证；截断读取不算完成，同一 CLI 上下文恢复不必重读。系统不再把这两段复制到单题黑板，Hook 也不注入公共原文；历史单题副本保留在历史记录，但不再重复交付。实时用户修正仍通过单题黑板增量发送。Worker 不直接查询 PostgreSQL，不依赖读取两个题目 JSON 文件来认领；第一次实际动作启动预算。
6. Worker 在自己的工作区保存结果，在 `/findings` 写 Finding。系统校验证据、导入黑板；新的最终候选会唤醒调度器，结束尝试、清理靶机并生成报告。

黑板交付使用 JSON 文本表示记录，但它不是读取磁盘 `question.json` 的结果。

## 原文与数据位置

```text
data/tasks/<批次ID>/
├── overview/
│   ├── scene.md         # 完整场景提示词
│   └── task.md          # 完整初始用户提示词，含原有接口/凭证
├── inputs/              # 开始任务前上传，Scout 专用
├── questions.json
└── <内部题目ID>/
    ├── source.json      # 题单原始条目，不写入 SQL metadata
    ├── question.json
    └── ...
```

不引入紧凑投影，不摘要或缩写公共说明。上述文件是批次原文的读取入口；保留现有单题题面与增量 Hook 协作机制。每题 `source.json` 也只读挂载为 `/question-source.json`，Worker 可按需查询题单中的其他原始字段。

## R04 的工作量控制

- 每轮调度只读取一份题目列表，在本轮复用认领、超时、解出后的返回记录；父任务阶段和 Worker/Reporter 状态真正变化时才 UPDATE。
- 单题快照先比较相关输入字段与靶机状态；无变化时跳过视图组装、JSON 编码、哈希和文件写入。附件索引缓存到附件登记发生变更；重复清单内容不重写。
- 存储层在成功提交题目、智能体、附件或黑板变更后发进程内通知。模型工具动作本身不必触发全量巡检；Token 统计、黑板 ACK 等无关元数据不会唤醒调度器。
- 调度使用 `asyncio.Event`，并按最近的尝试截止或靶机重试时间唤醒。靶机准备/关闭任务完成、Scout 结束/失败会唤醒；网络操作保持在原有后台任务中。
- 默认每 5 秒校准一次权威状态。附件采用一次批量查询校准，避免按题逐个查询；校准也会发现遗漏通知、缺失快照文件和服务恢复后的状态。事件等待不推迟预算截止。
- 并发认领锁和数据库原子 metadata 变更保留。批次退出时清理视图、附件与唤醒缓存；`question.json` 的靶场配置和两个文件的既有读取方保留。

本通知只负责当前控制进程的低延迟唤醒，不是跨进程消息队列；周期校准仍是可靠性兜底。没有引入 Redis、Celery、新服务或数据库结构迁移。
