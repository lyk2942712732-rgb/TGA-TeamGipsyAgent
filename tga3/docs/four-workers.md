# 四 Worker 执行

默认执行者为 `worker-openai`（Codex CLI）、`worker-claude`（Claude Code CLI）、`worker-opencode`（OpenCode CLI 1.19.5）、`worker-qwen`（Qwen Code CLI 0.27.0）。Scout 和 Reporter 的职责不变。

两种新 CLI 均支持项目现有的 Anthropic、OpenAI Chat Completions 和 Responses 端点，可在 Solver、新建任务、运行中的模型控制面板独立选择。API Key 通过环境提供；OpenCode 的配置仅存环境变量引用。模型切换在原有周期边界执行，保留原会话。

## AOE 调度

1. 收集阶段继续只派发简单题；全批无难度标记时按现有规则认领。四个空闲 Worker 可以并行领取四道不同的题目，任务锁和原子占用防止重复认领。
2. 每题最多两次独立尝试，由不同 Worker 执行。继续优先派发没有尝试过的题目，再按来源明确给出的难度排序。首次、第二次预算保持现有配置，从各次首条动作开始。
3. 保留整批阶段切换规则：全部题目已收集、剩余题目均完成两次独立尝试且无人仍在独立解题后，逐题共同攻坚。**该题的另外两位、未独立尝试过的 Worker** 接手；前两位无需同时空闲或恢复运行。
4. 攻坚两位使用各自的新会话，先读取本题黑板和公共原文，按需读取前两位的只读证据。`/evidence-logs/<agent>-actions.json` 的正文/附件路径相对于 `/evidence-files/<agent>/`，可复制相关脚本到自己的工作区修改。仅挂载本题的结果和已记录附件，CLI 会话状态仍在原 Worker 私有目录。
5. 共同攻坚两位共享一份预算，从第一条实际动作同时开始计时。中断恢复继续原攻坚会话和已有截止时间；超时放弃该题。完成一题仅结束该题及其报告，其他题继续。

### 最后一道题：围殴

四 Worker 任务中，已登记题目只剩一道未结束时，不论收集、首次/第二次独立尝试还是共同攻坚阶段，均切入 `swarm`（围殴）。不再等待两次独立尝试完成，也不受收集阶段“仅简单题”的限制；题面与附件仍须完成 Scout 交接，托管靶场仍须就绪。已解出或已放弃的题目不计入剩余数量。

- 四位 Worker 一起处理最后一题。正在解题的进程、CLI 会话和 attempt ID 保持不变；以前尝试过本题但未解出的 Worker 用自己的原生会话 resume，未尝试过的开新会话。原有手动暂停仍有效，解除暂停后再补入。
- **切入围殴时刷新已有 Worker 的时间，重新使用一份完整共同攻坚预算。** 已经开始实际解题时，统一 `started_at=切入时间`、`deadline=切入时间+joint预算`，运行中的 Worker 通过原 attempt ID 接收新的 deadline，不停进程、不丢上下文。若全体尚未有实际动作，则等围殴首条动作再统一起算。
- 预算为全体共享，不能每人各领一份；重复 tick、后来补入、暂停/恢复和控制面重启不会重新续时。旧阶段起算时间和截止时间保留在 `previous_started_at`、`previous_deadline` 中。
- 收集阶段按当前已登记题目判断；后来收集到的新题不会中断已经进入围殴的会话。围殴题结束后，其他题继续正常调度。历史两 Worker 任务维持原策略。
- 本题黑板保留并发布围殴协作提示。新加入者可读取同题历史只读证据；四位仍各自保留私有工作区和会话。成功会结束全部参与者；共享预算耗尽会放弃该题；原有 flag 提交收尾保护继续适用。
- 页面将其标为“共同攻坚（群殴）”，作为特殊共同攻坚展示倒计时和尝试记录。无需另设预算项，沿用 `aoe_attempt_budgets.joint`，历史均一预算仍兼容。

历史任务沿用它创建时已有的 Worker 记录。原两 Worker 任务继续使用原攻坚人员规则，历史记录和截止时间无需迁移。

### 首次尝试求援与增援

仅四 Worker 任务支持自动求援。正在进行的**首次尝试**同时满足以下两项才求援：已实际执行时间严格大于 10 分钟，且严格大于该 Worker 在当前任务内、同难度首次成功题目的平均耗时再加 3 分钟。没有有效同难度样本不自动求援；第二次尝试、共同攻坚与围殴均不触发。难度按已有等级归一化，同等级别的中英文标签共用样本，未知难度标签按原标签区分，未标难度不推测均值。

求援先标记为 `rescue.state=seeking`，并不暂停当前 Worker。有 Worker 空闲时，调度优先级为：最后一道题围殴 > 可认领题目中尝试人数少 > 难度低 > 给正在求援的题增援。只有本任务中手上没有题目、没有靶场准备预留且未被手动暂停的 Worker 才可加入；每题最多一名增援，不能抢占其他题的 Worker。

成功分配增援后记录 `reinforcement`，加入者 phase 为 `reinforcement`，关联原 `first_attempt_id`，求援状态变为 `reinforced`。原 Worker 的进程、会话、起算和截止时间均不变；增援者沿用原首次尝试的截止时间，不额外领取预算。增援者自己的参与耗时从加入时起记录。共享黑板及原 Worker 只读证据，现有提交收尾保护继续作用于全部参与者。

增援属于特殊首次尝试，会记入该 Worker 的已尝试记录，但不会消耗第二次独立尝试轮次。例如 A 首次、B 增援：首次失败后第二次从 C、D 中挑选；若选 C，则后续共同攻坚为 B + D。B 恢复其增援会话，D 开新会话。两人共享共同攻坚预算。增援中的题也能切入围殴，届时按围殴规则统一刷新所有参与者时间。

内部求援样本只取首次阶段成功记录，排除第二次、共同攻坚、围殴及无有效起止时间的记录。首次增援阶段解出时，被增援 Worker 始终获得成功归属，增援 Worker 只有实际解出时才获得归属；前端成功耗时、已解出数、各难度均值及内部首次成功样本遵守同一归属规则。实际解出方来自合法最终候选的 Worker 发布身份，保存在 `solver_agent_id`；各尝试的归属保存在 `success_credit`，不以“同阶段参与过”推断增援方解出。历史记录若无法确认增援方解出，不补造其成功归属。前端求援中、增援模式与首次增援尝试记录独立展示。

### Worker 战绩与累计耗时

概览展示当前任务中该 Worker 各难度已解出题目的平均累计投入；按题目的难度原值分组。均值分母为耗时完整的本人成功题目数，未解出、别人解出及耗时缺失的题目不混入均值。它与求援使用的“首次成功均值”是两个指标，不改变求援判定口径。

战绩分为上下并列的“已解出”和“未成功解出”。同一 Worker 多次参与同一道题只列一条，累计投入为各参与时段之和，不含两次参与间的等待；群殴切换前的历史投入也保留。已解出题目右侧只展示耗时数值，不加“累计投入”前缀、不另列成功阶段耗时；未成功题目只展示题名和状态，不展示耗时。本人尝试后由其他 Worker 解出的题目仍保留在本人的未成功列表，明确标注“其他 Worker 已解出”。进行中、已放弃及已取消题目均保留自身状态。

增援是特殊首次尝试：原 Worker 和增援 Worker 在该阶段解出时统一标为“首次尝试（增援）”；群殴是特殊共同攻坚，解出时标为“共同攻坚（群殴）”。实际进入后续普通共同攻坚才标“共同攻坚”，不因为曾参与过增援就改写其阶段。

题目总览的尝试记录按阶段编号，而非按 Worker 编号。同一阶段的参与者以“＋”合并为一条，例如“1. A＋B · 首次尝试（增援） · 已解出”和“3. C＋D · 共同攻坚 · 已解出”。普通共同攻坚切入群殴仍属于同一共同攻坚阶段，统一标“共同攻坚（群殴）”；直接从独立阶段进入群殴则保留真实发生过的独立阶段，再列共同攻坚阶段。阶段解出与个人成功归属分别记录，因此合并行仍展示全体参与者，但不会把未解出的增援方计入其个人成功统计。

已确认的暂停/恢复通过 `attempt.pauses` 记录，不改变阶段预算；展示累计时间时扣除这些区间，重叠时段合并，避免重复计时。停止容器的等待不计入结束后的解题耗时。历史数据若缺失起止时间则显示“未记录”并排除均值；历史未记录的暂停无法事后准确还原，不推测补造。

围殴预算耗尽且未解出时，明确记录 `finish_reason=joint_failed`，按共同攻坚失败直接放弃；不再回落到首次、第二次或普通共同攻坚重新尝试。

## CLI 与数据

- 复用已有 Debian/slim 工具基础镜像和 Python 环境；新镜像仅增加各自 CLI 包及项目代码。没有另装 Python 或增加控制服务。
- 两种 CLI 都调用现有常驻 HookService。OpenCode 使用原生插件的工具前后事件，Qwen 使用原生命令钩子。日志仍每位一个 `<agent>-actions.json`，原始正文仍在各自 `workspace/result/`。
- OpenCode 插件在模型消费增量前暂缓相应动作，不把暂缓记成一次执行；提交回执不会反复阻止下一条提交命令。并行动作、工具失败、中断和恢复均保留独立 action。
- `.opencode`、`.qwen` 和 `.tga3` 内部文件不参与输出附件扫描。两种 CLI 的实际 Token 回执以紧凑用量记录供现有统计模块增量读取、按原生消息/步骤 ID 去重。
- Finding、最终候选、平台成功回执校验、30 秒收尾保护、任务内经验卡和 Skills 沿用现有机制。卡片仍先提供完整紧凑目录，解题过程中按需读取。
- 知识库与项目 `web_search` MCP 均接入。Qwen 默认延迟展示 MCP 工具 schema，需用 `tool_search` 获取实际工具名/参数，再通过 `tool_call` 调用；这沿用 CLI 的省上下文机制。提示词明确说明了此入口。
