# TGA3 生产环境部署指南

## 1 推荐拓扑

当前版本推荐单台 Linux 主机部署：Nginx 对外提供 80/443，TGA3 控制面由 systemd 或发行版对应的服务管理器运行，PostgreSQL 由 Compose 运行，Worker 由控制面通过本机 Docker daemon 动态创建。

该部署需要对 Docker daemon 的访问权。`docker` 组等价于高权限，请将服务主机视为专用执行节点，不与不可信业务混部。

## 2 目录和运行账户

源码示例固定使用：

```text
/opt/TGA-TeamGipsyAgent/
├── apps/web/dist
└── tga3/
    ├── .venv
    ├── config
    ├── data
    ├── deploy
    └── compose.yaml
```

默认 Worker 镜像和 `runtime.json` 使用 UID/GID `1000:1000`。控制面创建任务目录时也要求该属主，因此生产运行账户的 UID/GID 应与之相同。先确认 UID 1000 对应的账户；在许多 Linux 安装中通常是首个登录用户：

```bash
deploy_user="$(id -un 1000)"
deploy_group="$(id -gn "$deploy_user")"
test "$(id -u "$deploy_user")" = "1000"
test "$(id -g "$deploy_user")" = "1000"
sudo usermod -aG docker "$deploy_user"
sudo mkdir -p /opt/TGA-TeamGipsyAgent/tga3/data
sudo chown -R "$deploy_user:$deploy_group" /opt/TGA-TeamGipsyAgent/tga3/config /opt/TGA-TeamGipsyAgent/tga3/data
sudo chmod -R u+rwX,go-rwx /opt/TGA-TeamGipsyAgent/tga3/config
sudo chmod -R u+rwX,g+rwX,o-rwx /opt/TGA-TeamGipsyAgent/tga3/data
```

确认该用户可访问 Docker：

```bash
sudo -u "$deploy_user" docker info >/dev/null
```

如果失败，重新登录或重启系统使组成员关系生效；不要通过公开 Docker TCP 端口绕过权限问题。如果服务器没有可用的 `1000:1000` 账户，应使用相同的自定义 UID/GID 重建基础 Worker 镜像，并同步修改 `runtime.json` 的 `worker_uid`、`worker_gid`，不能只改其中一侧。

自定义 UID/GID 的镜像构建方式如下，两个增量镜像必须在新基础镜像之后重建：

```bash
cd /opt/TGA-TeamGipsyAgent/tga3
run_user="your-service-user"
worker_uid="$(id -u "$run_user")"
worker_gid="$(id -g "$run_user")"
docker build --network=host \
  --build-arg "TGA3_WORKER_UID=$worker_uid" \
  --build-arg "TGA3_WORKER_GID=$worker_gid" \
  -f docker/Dockerfile.base -t tga3-ctf-base:local .
docker build --network=host -f docker/Dockerfile.openai -t tga3-worker-openai:local .
docker build --network=host -f docker/Dockerfile.claude -t tga3-worker-claude:local .
```

随后在 `runtime.json` 的 `docker` 对象中把 `worker_uid` 和 `worker_gid` 设置为上述数值，并让 systemd 使用同一账户。

## 3 安装 systemd 服务

以下命令适用于使用 systemd 的发行版，包括常见 Debian、Ubuntu、RHEL、Rocky Linux 和 AlmaLinux。使用其他服务管理器时，应保持相同的工作目录、启动命令、Docker 依赖和运行账户。

```bash
sudo cp /opt/TGA-TeamGipsyAgent/tga3/deploy/tga3.service /etc/systemd/system/tga3.service
deploy_user="$(id -un 1000)"
deploy_group="$(id -gn "$deploy_user")"
sudo mkdir -p /etc/systemd/system/tga3.service.d
printf '[Service]\nUser=%s\nGroup=%s\nSupplementaryGroups=docker\n' \
  "$deploy_user" "$deploy_group" \
  | sudo tee /etc/systemd/system/tga3.service.d/10-account.conf >/dev/null
sudo systemctl daemon-reload
sudo systemctl enable --now tga3
sudo systemctl status tga3 --no-pager
```

示例 unit 的启动过程：

1. 要求 Docker 已启动且网络可用。
2. 执行 `docker compose up -d --wait postgres`。
3. 执行 `.venv/bin/tga3 --config-dir .../config serve`。
4. 控制面异常退出时等待 3 秒重启。

查看日志：

```bash
journalctl -u tga3 -n 200 --no-pager
journalctl -u tga3 -f
```

## 4 安装 Nginx

Debian 和 Ubuntu 通常使用 `sites-available`：

```bash
sudo cp /opt/TGA-TeamGipsyAgent/tga3/deploy/nginx-tga3.conf /etc/nginx/sites-available/tga3
sudo ln -sfn /etc/nginx/sites-available/tga3 /etc/nginx/sites-enabled/tga3
sudo nginx -t
sudo systemctl reload nginx
```

如果发行版自带的默认站点也声明了 `default_server`，`nginx -t` 会报告重复默认服务器。此时只保留一个默认站点：可以禁用发行版默认站点，或从 `nginx-tga3.conf` 的 `listen` 行删除 `default_server` 后绑定正式域名。

RHEL、Rocky Linux 和 AlmaLinux 通常直接使用 `conf.d`：

```bash
sudo cp /opt/TGA-TeamGipsyAgent/tga3/deploy/nginx-tga3.conf /etc/nginx/conf.d/tga3.conf
sudo nginx -t
sudo systemctl reload nginx
```

### 4.1 SELinux 主机

RHEL、Rocky Linux、AlmaLinux 等启用 SELinux enforcing 的系统，需要为动态 Worker 挂载目录和 Nginx 静态目录设置持久文件上下文，并允许 Nginx 连接控制面：

```bash
sudo dnf install -y policycoreutils-python-utils
sudo semanage fcontext -a -t container_file_t \
  '/opt/TGA-TeamGipsyAgent/tga3/data(/.*)?'
sudo semanage fcontext -a -t httpd_sys_content_t \
  '/opt/TGA-TeamGipsyAgent/apps/web/dist(/.*)?'
sudo restorecon -Rv /opt/TGA-TeamGipsyAgent/tga3/data
sudo restorecon -Rv /opt/TGA-TeamGipsyAgent/apps/web/dist
sudo setsebool -P httpd_can_network_connect 1
```

不要通过关闭 SELinux 解决挂载或反向代理问题。若组织策略使用自定义类型，应由系统管理员替换上述通用标签。

示例配置提供：

- `/`：`apps/web/dist`，支持 SPA 路由回退。
- `/api/v3/`：反向代理到 `127.0.0.1:8083`，关闭缓冲并把读取超时设为 1 小时以支持 SSE。

Nginx 不代理 `/mcp` 和 `/internal/agents`。这些内部端点由 Worker 通过宿主网关直连 8083。

## 5 TLS

有正式域名时，将 Nginx `server_name _;` 改为域名，再按所在组织和发行版的证书流程配置 TLS。以下是 Debian/Ubuntu 使用 Certbot 的常见流程：

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d tga.example.com
sudo certbot renew --dry-run
```

RHEL 系发行版应通过其可用的软件仓库安装 `certbot` 和 Nginx 插件，证书申请参数保持一致。

在证书签发前确认 DNS 指向服务器，80/443 可从客户端网络访问。不要把 API 密钥写入 Nginx 配置。

## 6 网络边界

生产环境只应向用户开放 80/443，向运维网开放 SSH。以下端口不得对公网开放：

- 5433：PostgreSQL，仅绑定 `127.0.0.1`。
- 8083：控制面直连端口，供 Nginx、本机运维和 Docker Worker 使用。
- Docker daemon：不得监听无 TLS 的公网 TCP。

由于 Worker 需要从 bridge 网络访问 8083，防火墙规则应允许 Docker bridge 到宿主 8083，同时拒绝公网接口。优先在云安全组或上游防火墙关闭 8083，再按实际 Docker 网段设置主机规则，避免一条通用 deny 同时切断 Worker 回连。

## 7 密钥和配置安全

API 密钥存放在 `tga3/config/models.json`。建议：

- 文件属主为部署运行账户，权限为 600。
- `config` 目录权限为 700。
- 备份加密，恢复后重新检查权限。
- 不在工单、聊天、终端输出或日志中粘贴完整密钥。
- 定期轮换实际启用的 Provider 密钥。
- 对配置中心的网络访问增加上游身份认证或仅开放给可信内网。

当前应用自身未提供登录鉴权。若系统跨越可信内网边界，必须在 Nginx、VPN、零信任网关或其他上游层增加访问控制。

## 8 数据备份

完整可恢复备份至少包含：

1. PostgreSQL 逻辑备份。
2. `tga3/config`。
3. `tga3/data/inputs`、`artifacts` 和 `writeups`。
4. 如需恢复执行上下文，再包含 `data/workspaces`。

示例：

```bash
cd /opt/TGA-TeamGipsyAgent/tga3
deploy_user="$(id -un 1000)"
deploy_group="$(id -gn "$deploy_user")"
backup_dir="/var/backups/tga3/$(date +%Y%m%d-%H%M%S)"
sudo install -d -m 700 -o "$deploy_user" -g "$deploy_group" "$backup_dir"
sudo -u "$deploy_user" docker compose exec -T postgres \
  pg_dump -U tga3 -d tga3 --format=custom \
  | sudo tee "$backup_dir/database.dump" >/dev/null
sudo tar -C /opt/TGA-TeamGipsyAgent/tga3 \
  -czf "$backup_dir/files.tar.gz" config data/inputs data/artifacts data/writeups
sudo chmod 600 "$backup_dir"/*
```

定期在隔离环境执行恢复演练。备份成功不能替代恢复验证。

## 9 更新流程

1. 公告维护窗口，等待或停止运行中的任务。
2. 执行数据库和文件备份。
3. 记录当前提交：`git rev-parse HEAD`。
4. 拉取指定发布提交，不直接部署未固定的开发分支。
5. 检查 `schema.sql` 是否变化。
6. 重新安装 Python 包、构建前端，并在需要时重建 Worker 镜像。
7. 重启 systemd 服务，验证健康、配置和最小任务。

示例：

```bash
cd /opt/TGA-TeamGipsyAgent
git fetch --all --tags
git checkout <已审核的提交或标签>

cd tga3
.venv/bin/pip install '.[control]'
./scripts/build-images.sh

cd ../apps/web
npm ci
npm run build

sudo systemctl restart tga3
sudo nginx -t && sudo systemctl reload nginx
```

如果 `schema.sql` 变化且没有迁移脚本，停止更新并制定迁移方案。生产环境不得删除卷重建。

## 10 回滚

代码和镜像回滚必须与数据库 schema 兼容。回滚前：

- 保留当前数据库和文件备份。
- 切回记录的 Git 提交。
- 重建与该提交一致的 Worker 镜像和前端。
- 仅在确认数据格式兼容后启动旧版本控制面。

不要只回滚前端或只回滚 Worker 镜像后直接继续已有任务。

## 11 监控和维护

建议监控：

- `systemctl is-active tga3` 和 `/api/v3/health`。
- PostgreSQL 容器健康状态、磁盘和卷增长。
- Docker 镜像与停止容器占用。
- Worker 创建失败率、运行时长和内存峰值。
- `data/inputs`、`artifacts`、`writeups` 和 `workspaces` 容量。
- 模型 API 错误率、超时和配额。

常用命令：

```bash
systemctl status tga3 --no-pager
docker stats --no-stream
docker system df
df -h /opt /var/lib/docker
curl -fsS http://127.0.0.1:8083/api/v3/health
```

清理 Docker 对象前，先确认目标不包含仍需使用的 TGA3 镜像、数据库卷或任务容器。不要把 `docker system prune -a --volumes` 作为常规维护命令。

## 12 上线检查清单

- [ ] 使用固定、已审核的代码提交。
- [ ] PostgreSQL healthy，备份和恢复演练通过。
- [ ] 三个 Worker 镜像存在，基础工具自检通过。
- [ ] systemd 服务以专用账户运行并可访问 Docker。
- [ ] `config/models.json` 权限受限且密钥有效。
- [ ] 80/443 可访问，5433、8083 和 Docker daemon 不暴露公网。
- [ ] Nginx 的 SSE 超时和 SPA 路由回退正常。
- [ ] 配置中心受到可信网络或上游认证保护。
- [ ] 最小授权任务能够创建、运行、停止并下载报告。
- [ ] 日志、容量、备份和密钥轮换责任人明确。
