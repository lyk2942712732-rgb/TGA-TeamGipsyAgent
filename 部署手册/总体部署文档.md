# TGA3 总体部署文档

## 1 部署目标

本手册将 TGA3 部署为一套可持续运行的双 Worker 黑板协作系统。部署完成后，浏览器通过 React 前端访问 FastAPI 控制面；控制面持久化任务到 PostgreSQL，并在任务创建时动态启动 OpenAI Worker 与 Claude Worker 容器。

标准生产拓扑为单台 Linux 主机。PostgreSQL 由 Docker Compose 管理，控制面可由 systemd 或发行版对应的服务管理器管理，前端静态文件由 Nginx 提供。部署步骤以本目录的 `deploy.py` 为唯一编排来源，并复用源码中的 `tga3/compose.yaml`、镜像构建组件和服务配置示例。

## 2 组件和职责

| 组件 | 技术 | 运行位置 | 职责 |
|---|---|---|---|
| Web 控制台 | React 18、Vite 5 | Nginx 静态目录或 Vite | 任务、配置、Agent、报告和系统状态界面 |
| TGA3 控制面 | FastAPI、Uvicorn | Linux 宿主机 | API、SSE、WebSocket、MCP、调度和报告生成 |
| PostgreSQL | PostgreSQL 17 Alpine | Compose 容器 | 任务、黑板、对话、问题、Artifact 元数据和报告索引 |
| OpenAI Worker | OpenAI Agents SDK | 动态 Docker 容器 | 独立工作区内执行任务 |
| Claude Worker | Claude Agent SDK | 动态 Docker 容器 | 独立工作区内执行任务 |
| Nginx | Nginx | Linux 宿主机 | 静态前端、API 反向代理和可选 TLS |

Supervisor 和 Reporter 不是独立服务或常驻容器，而是控制面中的宿主 Agent。Worker 容器通过标签 `tga3.task_id` 和 `tga3.agent_id` 关联任务。

## 3 数据流和数据目录

```text
用户请求
  -> /api/v3/tasks
  -> PostgreSQL 写入任务和初始黑板
  -> Docker SDK 创建两个 Worker
  -> Worker 通过 WebSocket 接收周期指令
  -> Worker 通过 /mcp 同步黑板并登记 Artifact
  -> final_candidate 触发 Reporter
  -> data/writeups 生成 Markdown 报告
```

相对路径均以仓库内的 `tga3` 为基准：

| 路径 | 内容 | 备份级别 |
|---|---|---|
| `config/` | 模型、Agent、场景、运行时和 Skills 配置 | 必须，含密钥 |
| `data/inputs/` | 用户上传文件 | 必须 |
| `data/artifacts/` | Worker 持久证据 | 必须 |
| `data/writeups/` | 最终 Markdown 报告 | 必须 |
| `data/workspaces/` | 每任务每 Worker 的工作目录和私有会话 | 视恢复目标决定 |
| Docker volume `tga3-postgres-data` | 关系数据和任务状态 | 必须 |

## 4 网络和端口

| 端口 | 绑定 | 使用者 | 说明 |
|---|---|---|---|
| 80/443 | 公网或内网地址 | 浏览器 | Nginx 页面与 `/api/v3/` |
| 8083 | `0.0.0.0` | Nginx、Worker、运维 | 控制面、MCP、内部 WebSocket；应由防火墙限制公网 |
| 5433 | `127.0.0.1` | 控制面 | PostgreSQL 宿主映射 |
| 5173 | `127.0.0.1` | 开发浏览器 | Vite 开发服务 |
| 4173 | `127.0.0.1` | 本机验收 | Vite preview |

Worker 容器不对宿主映射端口。默认使用 Docker `bridge` 网络，通过 `host.docker.internal` 和 `host-gateway` 访问控制面。

## 5 部署顺序

1. 检查 Docker、Compose、Python、Node.js、npm、网络和磁盘。
2. 启动 PostgreSQL 并等待健康检查通过。
3. 构建 `tga3-ctf-base:local`、`tga3-worker-openai:local` 和 `tga3-worker-claude:local`。
4. 创建 `tga3/.venv`，安装 `tga3[control]`。
5. 在 `apps/web` 执行 `npm ci` 和 `npm run build`。
6. 启动控制面，并通过配置中心写入 Provider、模型和 Agent 绑定。
7. 开发环境运行 Vite；生产环境安装 systemd 和 Nginx。
8. 运行部署验证脚本，再创建最小测试任务验证动态 Worker。

## 6 配置原则

TGA3 的唯一配置源是 `tga3/config` 下的四个 JSON 文件和 `skills` 目录。Provider 地址、模型和 API 密钥不会被宿主环境变量覆盖。前端配置中心保存时会执行跨文件校验并原子写回。

以下修改需要重启控制面：

- `runtime.json` 中的 `listen_host`、`listen_port`。
- `runtime.json` 中的 `postgres_dsn`。
- 会影响宿主进程已建立资源的其他运行时参数。

Provider、模型、Agent、场景和 Worker 资源参数在新任务创建时生效；运行中的任务保留已记录状态。

## 7 部署方案

### 7.1 开发和演示

- PostgreSQL：`docker compose up -d --wait postgres`
- 控制面：`.venv/bin/tga3 --config-dir config serve`
- 前端：`npm run dev`
- 访问：`http://127.0.0.1:5173`

该方式便于查看日志和调试，不适合无人值守。

### 7.2 单机生产

- PostgreSQL：Compose `restart: unless-stopped`
- 控制面：systemd 自动重启
- 前端：Nginx 静态目录
- 对外入口：80/443
- 内部控制面：8083，仅允许本机和 Docker bridge 访问

这是当前源码直接支持、风险最低的生产部署方式。

### 7.3 Kubernetes

当前版本未提供 Kubernetes 资源清单，也没有把动态 Worker 调度改造成 Kubernetes Job。若需要 Kubernetes，必须重新实现容器运行时、持久卷、网络回连和权限模型，不能直接复用 Docker socket 方案。

## 8 验收标准

### 8.1 静态验收

- 四个 JSON 配置可解析，所需 Agent 和场景完整。
- Python 包安装完成，前端 `dist/index.html` 存在。
- PostgreSQL 容器为 healthy。
- 三个本地镜像存在，基础镜像工具自检通过。

### 8.2 运行验收

- `GET /api/v3/health` 返回 `{"status":"ok","service":"tga3"}`。
- 前端首页返回 HTTP 200，刷新任意前端路由仍回到 `index.html`。
- 配置中心能读取和保存配置。
- 创建授权测试任务后，两个 Worker 容器被创建并能连接控制面。
- 任务页可接收 SSE 对话更新，停止任务后 Worker 被回收。
- 最终候选产生后，报告能够下载为 Markdown。

## 9 运维边界

- 不要手工长期运行 Worker 容器。
- 不要将 5433、8083、Docker socket 或配置密钥直接暴露到公网。
- 不要并行运行多个 `部署手册/deploy.sh` 或镜像构建过程。
- 不要在生产数据库上执行 `docker compose down -v`。
- 不要将 `config/models.json` 提交到公开仓库或复制到低权限共享目录。
