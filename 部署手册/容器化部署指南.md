# TGA3 容器化部署指南

## 1 容器化模型

TGA3 使用混合容器化模型：PostgreSQL 是长期 Compose 容器，两个 Worker 是按任务动态容器，控制面和 Nginx 运行在宿主机。这样可以让每个 Worker 拥有独立工作区，并在任务停止后回收执行环境。

```text
PostgreSQL 17 Alpine      长期运行，Compose 管理
tga3-ctf-base             只作为镜像基础层
tga3-worker-openai        按任务动态创建
tga3-worker-claude        按任务动态创建
TGA3 control plane        宿主机进程，调用 Docker SDK
```

## 2 镜像分层

| 镜像 | Dockerfile | 内容 |
|---|---|---|
| `tga3-ctf-base:local` | `docker/Dockerfile.base` | Kali headless、通用安全工具、CTF Python 环境、非 root 用户 |
| `tga3-worker-openai:local` | `docker/Dockerfile.openai` | 基础镜像 + TGA3 源码 + OpenAI Worker 依赖 |
| `tga3-worker-claude:local` | `docker/Dockerfile.claude` | 基础镜像 + TGA3 源码 + Claude Worker 依赖 |

两个 Worker 共享基础 layer，不需要分别维护两套 Kali 工具镜像。

## 3 构建

```bash
cd tga3
chmod +x scripts/*.sh
./scripts/build-images.sh
```

脚本默认使用宿主网络构建，并允许指定：

```bash
KALI_MIRROR=https://mirrors.tuna.tsinghua.edu.cn/kali \
DOCKER_BUILD_NETWORK=bridge \
./scripts/build-images.sh
```

不要同时启动多次构建。基础镜像包含大量软件包，构建中断后应先查看失败层和磁盘，再决定是否重试；不建议立即清空全部 Docker 缓存。

## 4 运行时创建过程

创建任务时，控制面根据 `runtime.json` 和 Agent 绑定执行以下操作：

1. 创建任务级 input、artifact 和 Worker workspace 目录。
2. 将 workspace 和 artifact 设为 Worker UID/GID，并设置为 `0770`。
3. 选择 `worker_images` 中的镜像。
4. 以非 root 用户启动容器。
5. 挂载三个任务目录。
6. 注入已解析的 Provider、模型、密钥和周期提示。
7. 通过 `host.docker.internal` 回连宿主控制面。

Worker 容器名称格式为：

```text
tga3-<任务UUID前8位>-<agent_id>
```

容器标签包括完整 `tga3.task_id` 和 `tga3.agent_id`，运维应优先按标签定位，不依赖截断名称。

## 5 挂载和数据边界

| 宿主目录 | 容器目录 | 模式 | 用途 |
|---|---|---|---|
| `data/workspaces/<task>/<agent>` | `/workspace` | 读写 | 每个 Worker 独立工作目录和私有会话 |
| `data/inputs/<task>` | `/inputs` | 只读 | 用户上传文件 |
| `data/artifacts/<task>` | `/artifacts` | 读写 | 可持久化证据 |

不同 Worker 不共享 `/workspace`。公共事实通过 PostgreSQL 黑板和 MCP 交换。Artifact 文件可以共享，但必须先登记，并由服务端校验归属和可用性。

## 6 网络

默认网络为 Docker `bridge`。控制面启动 Worker 时增加：

```text
host.docker.internal -> host-gateway
```

容器内使用：

- `ws://host.docker.internal:8083/internal/agents`
- `http://host.docker.internal:8083/mcp/`

因此控制面需要监听可从 Docker bridge 到达的地址。若自定义 Docker 网络：

```bash
docker network create tga3-workers
```

再把 `runtime.json` 的 `docker.network` 改为 `tga3-workers`，并验证该网络能访问宿主网关。已运行 Worker 不会自动切换网络。

## 7 资源和安全

默认每个 Worker：

- 2 CPU。
- 4096 MB 内存。
- 512 个 PID。
- UID/GID `1000:1000`。
- `cap_drop=[ALL]`。
- 仅增加 `NET_RAW` 和 `SYS_PTRACE`。
- `no-new-privileges=true`。

`NET_RAW` 用于授权范围内的网络探测，`SYS_PTRACE` 用于任务空间内的二进制调试。不要增加 `SYS_ADMIN`、`--privileged`、宿主设备或 Docker socket 挂载。

Provider API 密钥会由控制面注入对应 Worker 的环境变量。任何能读取容器配置或 Docker daemon 的账户都可能看到密钥，因此 Docker 权限必须严格限制，诊断信息中不要提交完整 `docker inspect` 输出。

## 8 生命周期管理

查看运行中的 Worker：

```bash
docker ps --filter label=tga3.task_id
```

查看全部 TGA3 Worker：

```bash
docker ps -a --filter label=tga3.task_id
```

正常情况下应通过前端或 API 停止任务，由控制面先停止再删除 Worker。只有控制面已失效且确认任务不再需要时，才手工处理残留容器。

## 9 镜像更新

更新 SDK、TGA3 源码或基础工具后，应按顺序重建全部镜像。新任务使用新镜像；已经运行的容器不会自动替换。建议在维护窗口：

1. 停止或完成现有任务。
2. 记录当前镜像 ID。
3. 构建并运行基础镜像自检。
4. 构建两个 Worker 增量镜像。
5. 创建最小测试任务。
6. 验证后再清理不再需要的旧镜像。

## 10 Kubernetes 说明

当前代码直接使用 Docker SDK、宿主目录绑定和 `host-gateway`。迁移 Kubernetes 需要新增 Kubernetes 运行时适配器，把 Worker 映射为 Job 或 Pod，并重新设计 PVC、Secret、NetworkPolicy、回连地址和清理机制。在这些能力实现前，不提供或执行 Kubernetes 一键部署脚本。
